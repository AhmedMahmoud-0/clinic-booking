# Phase 2B — Appointments, Reception Queue, and Clinical Records

## Status

Schema-only design package. Apply locally and validate/generate/typecheck before treating it as accepted. No migration, seed, or database write is included.

## Models added

| Model | Purpose |
| --- | --- |
| `Appointment` | Patient booking with doctor/service references and booking-time duration/price snapshots. |
| `AppointmentStatusHistory` | Append-only record of appointment state changes and their source. |
| `QueueEntry` | Reception queue for checked-in appointments and walk-ins. |
| `IdentityVerification` | Records two identity elements, result, verifier, and timestamp without storing the presented identity values. |
| `Encounter` | The actual clinical visit; separate from the booking. Can originate from an appointment or a walk-in queue entry. |
| `ClinicalNote` | Structured SOAP note with draft/signed state. |
| `VitalSign` | Timestamped measurements recorded during an encounter. |
| `DiagnosisCatalog` | Reusable diagnosis reference list; no unreviewed codes are seeded here. |
| `EncounterDiagnosis` | Encounter diagnosis with a display-name snapshot and primary flag. |
| `Prescription` | Encounter prescription with draft/issued/cancelled lifecycle. |
| `PrescriptionItem` | Medication directions as a clinical record; no inventory/pharmacy workflow. |
| `ClinicalAmendment` | Append-only correction record for signed clinical notes. |
| `Referral` | Internal specialty/doctor or external-facility referral. |

## Business rules represented in the model

- Appointment and Encounter are separate entities. A booking may be cancelled/no-show without an encounter; a walk-in may have an encounter without a prior appointment.
- The appointment references a `DoctorService` through a composite `(doctorServiceId, doctorId)` foreign key, so the selected service must belong to the selected doctor. It stores `durationMinutes`, `bookedPrice`, and `currencyCode` snapshots. Later service-catalog changes must not silently rewrite an existing booking.
- The booking reference is generated by the application and must be unique. Do not expose internal cuid identifiers as public booking references.
- Guest bookings still resolve to a Patient record. Phone OTP is not required for guest booking; identity checks at reception are recorded separately.
- `IdentityVerification` stores the two kinds of evidence checked, not raw national-ID/passport values or copies of presented documents. Appointment status history can identify an employee or patient actor; system-originated changes have no person actor.
- Queue entry type differentiates a checked-in appointment from a walk-in. Walk-ins are represented only as queue entries, not as synthetic appointment bookings. A walk-in must not displace or rewrite a confirmed appointment.
- Queue numbers are unique per doctor and clinic-local queue date. The clinic time zone must be used when deriving `queueDate`.
- Clinical notes are draft or signed. A signed note is not silently overwritten; correction is appended through `ClinicalAmendment` with prior content, corrected content, reason, author, and timestamp.
- Vital signs are recorded as nullable typed values so a nurse can record only the measurements actually taken.
- Prescriptions store the clinician-entered medication name and directions. There is no medication inventory or pharmacy module.
- Referral rows distinguish internal and external targets. Cross-field validity rules will be enforced by application validation and PostgreSQL CHECK constraints in the reviewed migration.

## Important constraints for Phase 2E migration SQL

Prisma schema validation cannot express all of these rules. Add reviewed PostgreSQL constraints/indexes during Phase 2E:

1. `endsAt > startsAt`, positive `durationMinutes`, nonnegative `bookedPrice`, and valid currency length.
2. Prevent overlapping active appointments for the same doctor and for the same patient, including concurrent transactions. Use a PostgreSQL exclusion constraint with an explicitly reviewed range/status design; do not rely only on application-side prechecks.
3. Prevent `QueueEntry` rows where `type = APPOINTMENT` with no `appointmentId`, or `type = WALK_IN` with an `appointmentId`; confirm appointment/patient/doctor consistency. For a `STAFF` status change require `changedByEmployeeId`; for `PATIENT` require `changedByPatientId`; for `SYSTEM` require neither.
4. Enforce that `firstElement <> secondElement` and record exactly two distinct identity element types.
5. Ensure an Encounter is linked to exactly one origin: either an appointment or a queue entry. Enforce patient/doctor consistency with the origin.
6. Validate vital-sign ranges and nonnegative prescription duration, quantity, and refill count.
7. Enforce at most one primary diagnosis per encounter using a partial unique index.
8. For `Referral`, enforce internal targets versus external facility fields consistently.
9. Enforce state-dependent timestamps (e.g. a signed note requires `signedAt`; an issued prescription requires `issuedAt`).

The exclusion-constraint strategy must account for confirmed/active statuses and the approved cancellation/no-show rules. It must be reviewed against actual PostgreSQL behavior before applying.

## Authorization boundary

These tables contain sensitive patient and clinical information. The schema does not grant access. Authentication and server-side role/record-scope authorization remain Phase 3 prerequisites for all protected reads and writes. Reception views must not include clinical notes, diagnoses, prescriptions, or detailed reasons for visit. Nurse workflows must not create diagnoses or prescriptions independently.
