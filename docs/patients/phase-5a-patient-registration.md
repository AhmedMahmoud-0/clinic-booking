# MERUNO Phase 5A — Patient Registration & Duplicate Prevention

## Purpose

Create a safe reception workflow for a person who does not yet have a clinic patient record. This is an internal clinic registration flow, not public self-registration and not a Better Auth sign-up flow.

## Authorization boundary

Both endpoints require `CLINIC_PERMISSIONS.PATIENT_BASIC_MANAGE` through `withEmployeePermissionRoute`. In the existing role matrix this permission is assigned to Reception. Doctors, nurses, diagnostic staff, Cashier, Clinic Manager, and System Admin do not gain this patient-creation capability from this update. Do not widen the role matrix as part of this increment.

Both endpoints require JSON and a same-origin request using the existing Better Auth base URL check. Responses are `no-store` and vary by cookie/origin.

## API contracts

### `POST /api/reception/patients/duplicate-check`

Request:

```json
{
  "firstName": "Mariam",
  "middleName": "Ali",
  "lastName": "Hassan",
  "dateOfBirth": "1995-04-12",
  "phone": "+20 10 1234 5678"
}
```

`dateOfBirth` is optional/null, but phone is required for intake matching. Search candidates are retrieved by matching first/last name or normalized phone; middle name and date of birth refine the exact full-name match used for high-confidence blocking. Inactive as well as active patient records are included so a deactivated record cannot be duplicated. Phone contacts are not assumed globally unique because family members may share one phone number.

Response contains a bounded list of minimal candidates:

- `patientId`, `mrn`, `displayName`, and `dateOfBirth`.
- `matchedIdentifiers`: only `FULL_NAME`, `DATE_OF_BIRTH`, and/or `PHONE`.
- `confidence`: `HIGH` only when full name and date of birth both match; otherwise `REVIEW`. Phone comparison handles Egyptian local and `+20` formats, but a shared phone plus date of birth is still only `REVIEW` when the name differs. A shared phone alone is never a high-confidence duplicate.
- `truncated` indicates that more than 20 candidates were found for display.

The response never includes phone/email values or any appointment, clinical, diagnostic, or billing data.

### `POST /api/reception/patients`

Request:

```json
{
  "firstName": "Mariam",
  "middleName": "Ali",
  "lastName": "Hassan",
  "dateOfBirth": "1995-04-12",
  "gender": "FEMALE",
  "phone": "+20 10 1234 5678",
  "email": "mariam@example.com",
  "identityElements": ["FULL_NAME", "DATE_OF_BIRTH"],
  "duplicateReviewAcknowledged": false
}
```

Rules:

- MRN is generated by the server using cryptographically random bytes and is never accepted from the client.
- Exactly two different identity element types are required, and `FULL_NAME` must be one of them. Supported second elements are date of birth, phone, national ID, passport, or another clinic-approved physical identity element.
- If National ID/passport/other documents are checked, only the element type and verification result are recorded. The raw number/image is not collected in this increment.
- A future date of birth is rejected. Date of birth may be unknown where the second checked element is another supported identity element.
- Phone is required; email is optional. Contact values are stored with normalized values, but `verifiedAt` remains null because no phone/email OTP verification occurs here. Family-shared phone/email values remain allowed across different patient profiles.
- The server repeats duplicate checking inside a PostgreSQL Serializable transaction. A high-confidence match (exact full name + date of birth) blocks creation. Other possible matches require the receptionist to review the candidates and explicitly set `duplicateReviewAcknowledged: true`.
- Phone duplicate lookup checks both the submitted digits-only form and its equivalent Egyptian `+20`/national form. The database search therefore finds older rows regardless of which of those forms was stored in `normalizedValue`; patient records are not bulk rewritten.
- When a low-confidence candidate is acknowledged, a dedicated `PATIENT_DUPLICATE_CANDIDATES_REVIEWED` AuditLog event is written. The audit reason is fixed text and does not copy submitted names, phone numbers, or email values.
- Patient creation, the `IdentityVerification` record, and all AuditLog events commit atomically. A transaction serialization conflict returns HTTP 409 and asks the client to repeat duplicate checking. There is no partial patient record.

## Identity verification and privacy

The registration employee attests that two distinct identity elements were checked. `IdentityVerification.firstElement` and `secondElement` store element types, with `result = VERIFIED` and the employee ID. The notes explicitly state that raw values are not retained. This is an in-clinic identity check, not email or phone verification.

Public patient registration in Phase 3G-A remains separate: it creates only a Better Auth identity and never creates or links a clinic Patient record. A later patient-account linking operation still requires the existing two-identifier in-clinic check. No PatientAccount link is created automatically here.

## Existing database models reused

- `Patient`
- `PatientContact`
- `IdentityVerification`
- `AuditLog`

No Prisma schema changes, migration, seed change, Prisma Client generation, dependency, or environment variable are required. Existing patient and appointment records are not rewritten.

## Deferred work

This increment does not implement patient profile editing/deactivation, additional contact management, consent records, document attachments, family relationships, legal-guardian verification, patient account linking, appointment booking, or patient-facing screens. Those remain in later Phase 5, Phase 6, Phase 10, and Phase 11 increments as appropriate.
